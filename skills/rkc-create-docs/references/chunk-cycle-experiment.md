# Small-input local research and transfer pilot

Identity: `RKC-CREATE-FLOW-CHUNK-PILOT-1`.

## Scope and order

1. Orient, bound units and present one preflight.
2. Research, draft and source-check each unit locally.
3. Assemble checked fragments and verify seams.
4. Run accuracy QA, then task-usefulness QA, and mechanical checks.
5. Preserve diagnostic notes and report the actual outcome.

Keep the loaded master unchanged. This reference replaces only execution order,
the operation-wide assignment ceiling, diagnostic-note storage and QA allocation.
It does not replace evidence rules, knowledge selection, English documentation,
source protections, mutation boundaries or completion requirements.

## 1. Orientation, boundaries and one preflight

Use the master's read-only inventory and inspect enough source to identify
consequential behavior units and feasible document routes. A unit is a behavior
chain with its state owner, immediate implementations, consumers and tests.
Do not split by directory, equal bytes or file count; split when materially
different behavior or a chain too wide to check requires another unit. Shared
helpers do not prove equivalent conditions or outcomes. Include the branches
and adjacent implementations that can change the rule.

Record a short working scope: unit entry points and files, external edges,
inspected-but-excluded sources with reasons, and material unchecked scope.
Read whole relevant implementations, not just search hits. An inventory is
not a claim that every listed source has been investigated.

This first pilot handles at most two consequential units, processed sequentially.
The primary agent researches and writes; use no separate research worker.
Allow at most five scoped read-only assignments in total: one local checker per
unit, one seam checker only when a material seam needs it, and two final QA
reviewers. Run no more than one delegated assignment at a time. These explicit
limits replace the master's three-assignment ceiling; do not spend assignments
on mirrored summaries or additional discovery. This is not a whole-repository
scaling policy. If necessary coverage exceeds the pilot bounds, report that
limit and do not claim the whole repository was covered.

Present the master's single preflight after orientation, before writing any
files. Explain proposed routes and material evidence limits. Full local research
and drafting follow approval rather than finishing all broad research first.
Obtain no per-unit approvals. Ordinary approval authorizes the documentation-only
scope and diagnostic notes outside the target. Respect existing session authority.
A partial source checkout is not evidence about absent production capabilities;
do not invent build commands or a complete application architecture for it.

## 2. Research, local draft and source check

For one unit, inspect consequential conditions, alternate outcomes, writers and
consumers, update units, identifiers and evidence boundaries. For asynchronous
work trace when mutable state is read, what is checked after waiting, and the
observable result of failure or completion. Verify implementation and test setup;
a helper name, a test title or an imported library is not a complete contract.

Before condensing, preserve the primary's original findings in a bounded note.
Use short identifiable statements: rule and acting condition/exception, source
path and symbol, strength and boundary of evidence. Keep inferences, external
dependencies and open questions separate. Record relevant residual sources and
edges that were not investigated. Do not create a schema or one note per function.

Draft the actual topical passage immediately while this source context is
available. Choose sections/files by the master's task routes and coherent scope,
not by the number of units. Save its pre-review text in diagnostic storage so
corrections remain distinguishable from initial findings. Drafts may be provisional
until assembly, but must retain conditions and unresolved material limits.

Give the local checker the brief below, the unit's source entry points, original
findings and actual draft paths. Include the selected revision/evidence scope and
a worktree baseline distinguishing owner work, operation drafts and protected
files. Pass no benchmark answers, expected topics, previous evaluation reports,
the entire master or source dumps. Wait for the result before advancing.

### Local checker brief

Read the assigned implementation, immediate consumers and relevant test setup,
the original findings and the actual draft. Review two directions separately:
source to finding accuracy, and finding to passage retention. For every distinct
consequential rule in this unit, check acting conditions, exceptions, outcome,
data/update boundary and evidence limit. Locate the actual passage; a heading,
shared helper or grouped RETAINED label is not proof. Read relevant excluded
sources and outgoing relationships that could qualify or contradict the rule.
Report material behavior supported by the unit sources but absent from findings
as well as inaccurate findings and lost conditions. Do not require ordinary local
details to become documentation or invent an omission to satisfy the review.
Challenge categorical claims with relevant counterexamples. Distinguish local
implementation from external/runtime guarantees and test use from test coverage.
Return a bounded plain-text disposition per consequential rule, with source and
passage anchors, confirmed discrepancy/correction or supporting evidence, and
unchecked scope. Use primary evidence, not agreement with the author. Modify no
files, execute no product code, install nothing and contact no external systems.

### Correction and continuity

Keep original findings and reviewer output immutable. Record verified corrections
and their disposition beside them. Allow one correction cycle per unit, then
recheck changed rules and dependent statements against source and actual text.
Do not silently add another research/review cycle. A confirmed blocking defect
remaining after the cycle stops progression; missing checks remain disclosed limits.
Do not promote a finding to verified merely because two reports agree.

If delegation is unavailable, perform the same separate source pass yourself
and disclose that independence was unavailable. Do not bypass host permissions.
After each unit, preserve checked passages, pending edges and correction status
before leaving its context. Resume from originals and checked dispositions,
rechecking only evidence affected by changed source or scope.

## 3. Assembly and seams

Assemble checked passages into canonical homes, AGENTS and task routes. Retain
material conditions; merge only proven equivalent behavior. Do not turn a local
claim into an all/always/never rule or erase a distinct case while shortening.
Record material passage changes during assembly and recheck each altered rule.
Original fragments are diagnostic evidence, not templates requiring publication.

Check consequential cross-unit edges and shared conversions against both sides:
producer/consumer, state owner, identifiers and units, routing/registration,
ordering, defaults, exceptions and failure outcomes. For a material seam use the
remaining seam assignment with the same read-only baseline and protections;
otherwise perform a separate primary source check. Do not invent a seam for a
single unit or claim it was independently checked when no checker ran. If one
side is unavailable, retain that evidence limit. Preserve seam findings and
verified dispositions; permit one targeted correction/recheck, not a new sweep.

## 4. Two final QA assignments

Run these sequentially on the assembled output in fresh reviewer contexts.
Use the master's read-only QA protections and worktree baseline. Give actual
document paths, source entry points, revision and scope, not author conclusions.
Preserve complete returned reviews. Correct confirmed issues and source-check
changed claims once between reviews and after the second review. A targeted
recheck is not another complete QA. Disclose unavailable independence/checks.

### Accuracy QA brief

Review actual entry points, routes, broad rules and consequential topical claims
against relevant code, test setup and declared source scope. Check material
conditions and counterexamples to categorical statements, producer/consumer
connections, asynchronous outcomes and completion versus newer state. Distinguish
repository facts, inference, external behavior and intent. Examine a bounded
high-impact source area not represented by the draft's headings when the inventory
supports it; conclude either adequate local recoverability or missing knowledge
from evidence. Do not independently rediscover the whole repository. Return
confirmed discrepancies, supporting source/passages, severity, narrow correction
and material unchecked scope. Modify nothing and perform no unauthorized execution.

### Task-usefulness QA brief

Select one realistic maintenance task from source entry points before reading
the topical explanation; select two only for materially distinct units. Follow
AGENTS and routes through documentation to the immediate owners, source and checks.
Judge whether the text retains the constraint that changes the implementation
plan, identifies the update boundary and supplies meaningful verification with
honest limits. Inspect source to judge sufficiency, without implementing the task.
Return task outcome, actual document/source anchors, narrow corrections and
unchecked scope. Modify nothing and perform no unauthorized execution.

Then perform the master's mechanical checks on all created/modified managed
documents, including untracked files, and apply its actual completion rules.

## 5. Diagnostic retention and reporting

Use safe host-provided storage outside the target for a short index, original
unit findings, pre-review fragments, complete local/seam/final reviews and verified
correction dispositions. This is the explicit exception to the research-file ban.
Index only existing files or exact conversation locations, never planned notes.
Keep notes available after completion/interruption and report their location so
the owner can preserve them. If safe storage is unavailable, preserve original
messages and passages in the conversation and disclose the retention limitation.
Do not ask the owner to request notes or supply extra process instructions.

Create no target-local research reports, progress files, `.rkc` state, knowledge
manifest or semantic IR. Copy no secrets, personal data, environment paths or
source dumps into notes. Preserve existing host files and owner work.
Record actual assignments and any exceeded/unavailable pilot limits in diagnostic
notes, not durable repository knowledge. Never invent token or time measurements.
Keep the owner's final report concise under the master's rules, adding only the
diagnostic location and material pilot limits. Keep unresolved facts unresolved.
