# RKC 2.1.0 candidate: rationale and validation

This is a maintainer evaluation plan, not a template for target repositories or
an instruction to load more documents on ordinary coding tasks. It is not
included in the npm payload. Candidate implementation is ready for package
validation; documentation-quality improvement remains to be evaluated.

## Conclusions and scope

Keep the existing progressive disclosure architecture: a compact root
`AGENTS.md`, one canonical task router, optional orientation documents, and
cohesive flow/domain documents selected by repository evidence. Do not require
a fixed file count, an operating-rules file, a universal checklist, or a
particular stack. Root README serves human orientation, the architecture map
explains ownership and boundaries, and flow documents explain runtime order
and consequential outcomes. Avoid duplicating these responsibilities.

A reference documentation set can preserve useful nuances while also carrying
duplication and stale claims. Its size and structure are not the target.
Prioritize accuracy, consequential coverage, change/verification guidance, and
routing before removing repetition. Total size and file count are not quality
targets; topical documents may grow when useful knowledge requires it. Keep the
shared entry concise without imposing that brevity on domain or flow knowledge.
Preserve verified contracts that change a future agent's location, plan,
implementation, or checks, including conditions, exceptions, and scope. A named
feature is not necessarily a sufficiently documented feature. Existing code/tests remain
primary evidence, and source inspection is selective rather than exhaustive.

The candidate retains three refinements to the existing master prompt:

1. For recurring changes with non-obvious multi-module dependencies, retain
   concise guidance about affected owners/contracts, related paths, and
   meaningful verification in the existing topical home. Do not add a
   procedure for every local change.
2. Explain material test coverage boundaries from setup, assertions, mocks,
   and runtime wiring. Follow the project's test conventions. Where manual
   acceptance is necessary, state preconditions, actions, and expected
   observable outcomes, keeping expected and executed checks distinct.
3. Keep consequential knowledge in routed documentation. Existing local API
   documentation, JSDoc/docstrings, or schemas supply precise module detail;
   short comments explain consequential non-obvious decisions. Do not move
   documentation into comments, prescribe mass commenting, or modify target
   source during documentation operations.

Bounded QA now checks both missing coverage and a consequential feature that
is already named but only briefly represented. Within the same small sample,
follow a plausible maintenance task to its constraint, writer/consumer, and
meaningful check. This changes the acceptance question, not the number of
reviewers or repository sweeps. Assess sufficiency and supporting/contradicting
evidence neutrally; do not reward smaller output or require findings. Merging
must preserve each area's task signals, contracts, conditions, and exceptions.
Useful existing documentation is reconciled with current evidence rather than
ignored or compressed merely to save space. Update and Audit keep the same
narrow scope.

Useful knowledge should grow through authorized implementation work and
bounded Update/Audit operations. Prefer an existing home; split only when a
cohesive reusable task route no longer fits. No automatic audit, mandatory
commenting pass, target dependency installation, knowledge manifest, RAG, or
documentation migration is introduced.

## Evaluation status and revised acceptance

The first controlled candidate evaluation showed useful change guidance and
clearer test boundaries, but also lost consequential knowledge and introduced
semantic regressions. Smaller output did not establish better documentation.
The candidate is not yet accepted for documentation quality. Prompt 2.16
clarifies priorities and preservation during synthesis; retain the previous
output as an experimental result rather than silently replacing it.

Repeat from the same documentation-free source baseline in a separate branch
of the existing evaluation repository. No new repository or worktree is needed.
Keep comparable model/host/settings and record the installed prompt revision
and exact candidate identity. Do not give the generator comparison findings,
prior outputs, or expected answers. Compare both candidate iterations with the
previous release output and current primary evidence. Register task cases
before the repeat, including cases outside the earlier findings. Manual fixes
to an output may help its repository, but do not demonstrate generator repair.

## Package validation

Use the supported Node.js 24/npm 11 environment:

```sh
npm ci
npm run release:check
```

Also run `npm run check:changed -- <each changed file>` for the exact candidate,
including this plan. The release gate builds a local tarball and checks
installation, lifecycle, and interrupted-process recovery. The install E2E
checks that the installed prompt equals the source candidate and that prompt
metadata agrees. It cannot prove documentation usefulness.

The local package is written under `artifacts/local-package/`:

```sh
npx --yes --package ./artifacts/local-package/repository-knowledge-compiler-2.1.0.tgz rkc install
npx --yes --package ./artifacts/local-package/repository-knowledge-compiler-2.1.0.tgz rkc version
npx --yes --package ./artifacts/local-package/repository-knowledge-compiler-2.1.0.tgz rkc doctor
```

These commands activate the candidate user-scoped installation and skills;
they do not publish it. Check that the active version is `2.1.0` and that the
installed core manifest and prompt identify `RKC-DOCS-CREATE-2.16`. Do not use
npm `latest` or `self-update` to activate an unpublished candidate. The package
gate uses isolated test homes; the owner's local install changes their active
RKC version.

When revising an already installed unpublished candidate with the same version,
repeating `install` verifies and reuses the existing core directory rather than
replacing its bytes. It can refresh skills from the new package, so do not use
that as proof of a fully refreshed candidate. Finish any running operation
before arranging a clean candidate installation; do not change installation
state during the controlled generation run.

## Controlled documentation evaluation

1. Preserve the reference and previous generated documentation branches.
   Create a new evaluation branch in the existing repository from the exact
   documentation-free source baseline used by the previous run. Inspect its
   status and initial document surface; do not remove documents from a working
   branch merely to prepare a test.
2. Confirm that source, tests, configuration, dependency files, and CI match
   the previous run. Record the source commit, installed package/prompt
   versions, model, host, relevant settings, and verification permissions in
   the evaluation record outside the generation session's evidence scope.
3. Start a fresh coding-agent session on that branch and invoke
   `/rkc-create-docs`. Give the same source-evidence boundary and comparable
   settings. Do not expose the reference docs, previous generated docs,
   evaluation findings, this plan, or expected answers; do not permit research
   through other branches or historical documentation. Existing instructions
   present in the shared baseline remain part of the controlled input.
4. Review and approve the ordinary preflight. Let Create complete its own
   semantic QA and mechanical checks. Record limitations honestly. Confirm
   that product source and protected files were not changed, then commit the
   generated documentation on the evaluation branch.
5. Compare three surfaces: reference documentation, previous generated
   documentation, and candidate-generated documentation. The principal
   comparison is previous versus candidate output; the reference supplies
   evidence-backed comparison material, not a required structure or truth
   oracle. Verify consequential disagreements against the common source.
6. Use a bounded set of six to eight realistic maintenance tasks, selected
   before inspecting the new output. For each, assess route clarity, retained
   behavioral constraints, change guidance, checks and their limits,
   unsupported claims, and unnecessary reading. Tasks selected from earlier
   findings measure targeted repair; reserve additional tasks not selected
   from those findings to assess broader usefulness.
7. If feasible, ask fresh agents to investigate equivalent tasks with one
   documentation set each. Keep prompts and permissions equal and avoid
   leaking the comparison answers. Measure actual source reads, context/tokens
   where available, and contract violations; do not infer these measurements
   from text size. Without this experiment, report structural usefulness only.

## Acceptance and next decision

Compare outcomes against the goals without assuming the candidate must win.
Accept the refinements when useful change/verification knowledge becomes
discoverable, source-supported constraints remain intact, and routing avoids
unrelated reading. Judge duplication and speculative procedures separately from useful
depth. New files, greater total volume, or a larger task-relevant document are
acceptable when needed knowledge justifies them; shorter output is not a win.
Check merged areas for retained conditions, exceptions, and tasks, not only
for headings or source lists.

Record unresolved regressions and adjust the narrow rule responsible rather
than adding domain examples or blanket instructions. One run is sensitive to
model variability; repeat when conclusions are ambiguous. A successful external
repository evaluation supports acceptance there, not universal performance.
Before claiming cross-stack improvement, use another repository with different
architecture or language.

After the evaluation, decide whether to revise, defer, or accept `2.1.0`.
Before promotion or separately authorized publication, rerun required checks
if candidate bytes changed and finalize release notes from verified results.
